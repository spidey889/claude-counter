# Claude Counter behavior

- The extension and standalone userscript share the same UI, constants and stylesheet. Keep their embedded copies synchronized when editing them.
- On home/new-chat pages, the usage row retains its original position inside the input card below its controls. In started conversations (`/chat/<id>`), it is the last child of `[data-cds="ChatComposer"]`, after the model selector and toolbar footer but outside the input card. Keeping it in the composer makes the dock include its height. The chat row has no extra top margin, aligns to the native 8px inset, and reserves 12px below the bars so they stay clear of the bottom edge. The existing URL-change handler switches placement when a chat starts or the user navigates back to New. The original model-selector placement remains a fallback for older layouts. A DOM observer uses the same placement rules to reconnect the row when Claude replaces the composer or its footer.
- Both usage tracks appear immediately in the original outlined box style (10px high with a 1px border). While both windows are unavailable, the row shows simple Session/Weekly labels, compact empty boxes, and one "Waiting for usage" message. This state has no fabricated percentages or countdowns. Once either window provides usage (including an actual 0%), the original percentages, reset countdowns, markers and warnings are shown. An absent weekly window is hidden when session data is available.
- The manifest installs the page-context network/history bridge in the `MAIN` world at `document_start`, before Claude can cache `fetch`. The UI and tokenizer load separately at `document_idle`. The isolated client waits for a bridge handshake instead of injecting a script tag after page load; the handshake replays the latest quota event received before the UI connected.
- Account usage is fetched on new-chat pages and existing conversations. REST utilization is a percentage; SSE `message_limit` utilization is a fraction converted to a percentage. Free accounts can return null REST windows, so normal replies supply the usage values through their live stream. The extension never sends an extra message to obtain usage.
- Stream parsing reads complete SSE events, using `event: message_limit` or the legacy JSON `type`. It handles multiline data, split CRLF endings, and the final data line at stream close. Responses are cloned so Claude keeps its original stream. Completion detection accepts both a POST `Request` object and fetch options.
- Clicking the row refreshes usage. Window rollovers and an hourly safety check also refresh it. The hourly check counts failed/null fetch attempts so free accounts do not generate a request every second.
- Token counting, conversation fetching and cache calculations retain the original author's behavior. The userscript uses the same stream parser and replays a quota event received before DOM initialization.

## Verification

Run `node --test tests/usage-flow.test.cjs`, `node --check` on changed JavaScript, check the embedded userscript copies against the source, and use `git diff --check`. The flow tests load scripts according to the manifest and cover a page-cached fetch, null REST windows followed by a reply, quota conversion, stream preservation, split/multiline SSE, Request objects, and early-event replay. Browser checks must cover `/new`, an existing chat, empty usage, and real usage values. Reload an installed unpacked extension and refresh Claude after changing its source; on free accounts, send a normal message to obtain a fresh quota event.
